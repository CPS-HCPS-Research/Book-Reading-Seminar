# CPS-HCPS Research 图书研讨仓库使用说明

本仓库用于组织CPS、HCPS及相关基础理论与智能软件研究的长期教材研读。成员在这里查找教材和研讨安排，提交原创笔记、PPT、Demo与习题解答，并保留讨论结论和后续任务。

正文以中文为主，教材原名、专业术语及必要的技术标识可保留英文；**文件和文件夹使用英文名称**，具体路径采用英文字母、数字和连字符，保留约定的扩展名与系统文件名。仓库名称固定为 `Book-Reading-Seminar`。

本说明面向参与学生、汇报人、审阅人和维护者。日常协作规则以[CONTRIBUTING.md](../CONTRIBUTING.md)为准；管理员设置和首次发布操作见[maintenance.md](maintenance.md)。本文件解释如何实际使用这些规则，不另设一套日程或材料副本。

## 快速开始

第一次参与时，按下面顺序操作即可：

1. 在[教材目录](../CATALOG.md)选择教材，阅读其README和资源表，确认使用的版次。
2. 查看[整体安排](../SCHEDULE.md)及教材的章节计划，确认自己负责的范围。没有任务时使用“研讨任务安排”Issue与负责人确认。
3. 从工作分支准备材料，将笔记、PPT、Demo和习题分别存入教材目录对应位置。
4. 运行本地检查，填写PR模板，关联任务Issue并请成员审阅。
5. 研讨后修订材料，由记录人补充真实日期的研讨记录和后续任务。

仓库已发布，可从[GitHub首页](https://github.com/CPS-HCPS-Research/Book-Reading-Seminar)访问。首次发布状态与网络故障时的恢复方法见本文末节，主分支保护配置见维护说明。

| 要完成的事情 | 从哪里进入 |
| --- | --- |
| 查当前教材 | [CATALOG.md](../CATALOG.md) |
| 查已确认时间和分工 | [SCHEDULE.md](../SCHEDULE.md) |
| 查LFCPS章节及背景 | [教材README](../books/LFCPS/README.md) |
| 查LFCPS章节任务 | [教材schedule.md](../books/LFCPS/schedule.md) |

| 了解提交要求 | [CONTRIBUTING.md](../CONTRIBUTING.md) |
| 查讨论结果与后续任务 | [sessions/README.md](../sessions/README.md) |

## 仓库结构与文件职责

组织方式是“教材为主要单位、材料类别为次级单位、研讨记录为过程索引”。同一份材料只保存一处，计划、任务与记录通过链接关联。

```text
Book-Reading-Seminar/
├── README.md
├── CATALOG.md
├── SCHEDULE.md
├── CONTRIBUTING.md
├── .gitignore
├── books/
│   └── LFCPS/
│       ├── README.md
│       ├── schedule.md
│       ├── resources.md
│       ├── notes/
│       │   ├── README.md
│       │   └── ch01-overview-example.md
│       ├── slides/README.md
│       ├── demos/README.md
│       └── exercises/README.md
├── sessions/README.md
├── templates/
│   ├── book.md
│   ├── notes.md
│   ├── presentation.md
│   ├── demo.md
│   └── session.md
├── .github/
│   ├── PULL_REQUEST_TEMPLATE.md
│   ├── ISSUE_TEMPLATE/
│   │   ├── book-proposal.md
│   │   ├── seminar-task.md
│   │   └── question-errata.md
│   └── workflows/check.yml
├── scripts/
│   ├── check_repository.py
│   └── tests/test_check_repository.py
└── docs/
    ├── user-guide.md
    └── maintenance.md
```

| 文件或目录 | 维护内容 | 更新时机 |
| --- | --- | --- |
| `README.md` | 首页、当前教材和常用入口 | 新增教材或导航变化时 |
| `CATALOG.md` | 教材基本信息、负责人、教材级状态和入口 | 新教材加入或状态变化时 |
| `SCHEDULE.md` | 跨教材的已确认日历、角色分工、任务与记录链接 | 时间和人员确认、延期或会后整理时 |
| `CONTRIBUTING.md` | 提交流程、命名、版权与质量要求 | 规则经团队讨论调整时 |
| `books/ID/README.md` | 单本教材档案、研究价值和章节导航 | 档案建立、版本变化或入口更新时 |
| `books/ID/schedule.md` | 章节范围、任务Issue、进度及材料PR | 任务认领与阶段推进时 |
| `books/ID/resources.md` | 官方资源、获取方式、版本和核实日期 | 发现官方资源变化或链接失效时 |
| 四类材料目录 | 原创学习资料及分类索引 | 提交和修订材料时 |
| `sessions/` | 实际研讨内容、结论、遗留问题和任务 | 研讨结束后 |
| `templates/` | 可复制的写作结构和必填项 | 模板确有改进需要时 |
| `.github/` | Issue、PR模板及自动检查工作流 | 协作机制变化时 |
| `scripts/` | 仓库检查器及其测试 | 检查规则或实现变化时 |

整体时间以 `SCHEDULE.md` 为准。教材计划不再维护一份独立日历，研讨记录不再复制一套PPT或Demo，避免多处版本不一致。

## 角色与责任

| 角色 | 主要职责 |
| --- | --- |
| 仓库维护者 | 维护协作规则、审阅与合并PR、处理仓库设置和归档 |
| 教材研讨负责人 | 确定研读范围、协调分工、维护教材状态和章节计划 |
| 汇报人 | 阅读、编写笔记与PPT、准备适用Demo、回应审阅意见 |
| 审阅人 | 核对概念、推导、引用、版权与运行说明，指出待修正问题 |
| 记录人 | 记录实际讨论、分歧、结论、未解决问题与后续任务 |
| 参与者 | 提前阅读、提出具体问题、参与讨论及认领后续任务 |

角色可以兼任。称为“独立复核”的Demo检查应由另一位成员实际执行，并记录复核者、环境和结果。未确认的人员写“待指定”，未确认的日期写“待定”；模板中的角色不代表已经安排了某位成员。

## 教材档案与研读状态

每本教材使用一个稳定ID，例如 `LFCPS`，并建立独立目录 `books/LFCPS/`。ID不随每次研讨或汇报人变化；不要因为同一本书换了一轮研读就复制整套目录。

教材档案至少登记书名、作者、出版社、年份、版次、语言、ISBN或DOI、官网、获取方式、学习状态、负责人以及版权限制。标识符缺失时如实说明，不自行生成。不同版次的页码或章序变化应在档案中说明，旧笔记保留其原版次定位。

教材级状态采用以下含义：

| 状态 | 含义 |
| --- | --- |
| 提议中 | 已提出研读建议，范围和组织安排尚待讨论 |
| 准备中 | 正在建立资料、确认范围或组织人员 |
| 研读中 | 已进入实际研读与研讨过程 |
| 已暂停 | 暂停；需要记录原因和后续处理方式 |
| 本轮完成 | 本轮约定范围已完成整理，有材料和真实记录支撑 |
| 已归档 | 本轮资料已归档，保留供检索和复习 |

章节任务可使用“未开始、准备中、待审阅、已研讨、已整理”。教材建档、示例文件存在或PR合并，均不能自动推出章节已经研讨。“本轮完成”表示本轮约定范围完成，不代表书中所有问题都已研究清楚。

## LFCPS教材入口

首本教材为 André Platzer 的 *Logical Foundations of Cyber-Physical Systems*，Springer, Cham，2018年英文第1版。精装ISBN为 `978-3-319-63587-3`，电子书ISBN为 `978-3-319-63588-0`，DOI为 [10.1007/978-3-319-63588-0](https://doi.org/10.1007/978-3-319-63588-0)。书目信息与获取方式见[Springer出版记录](https://link.springer.com/book/10.1007/978-3-319-63588-0)。

本书可用于研读混合系统建模、微分动态逻辑、形式化规格、不变式和演绎验证，以及混合博弈和运行时验证等主题。应用到HCPS时，人类行为、感知和决策权限等假设需要另行建立，不能直接假定教材已经解决这些问题。

| 内容 | 入口 |
| --- | --- |
| 教材档案及21章导航 | [books/LFCPS/README.md](../books/LFCPS/README.md) |
| 建议研读分组及任务进度 | [books/LFCPS/schedule.md](../books/LFCPS/schedule.md) |
| 官网、课件索引、视频、课程、勘误和工具 | [books/LFCPS/resources.md](../books/LFCPS/resources.md) |
| 原创笔记 | [notes/README.md](../books/LFCPS/notes/README.md) |
| 学生PPT及PDF | [slides/README.md](../books/LFCPS/slides/README.md) |
| 实验、模型与证明说明 | [demos/README.md](../books/LFCPS/demos/README.md) |
| 原创习题解答 | [exercises/README.md](../books/LFCPS/exercises/README.md) |

正式章号依据[作者公开目录](https://www.lfcps.org/lfcps/lfcps-toc.pdf)整理：第1章为概览，其后四部分分别覆盖第2–9、10–13、14–17和18–21章。仓库中的中文主题说明用于检索，不是官方中文译名。详细资源核实日期、页数口径差异和入口限制保存在资源表中。

初始[示例笔记](../books/LFCPS/notes/ch01-overview-example.md)用于展示写法，不能作为学生已经完成精读或实验的证据。

## 材料分类与命名

所有自定义路径使用英文。教材ID使用大写英文缩写；材料主题与作者标识使用小写英文字母、数字和连字符。文件正文、PPT内容和图表说明可以使用中文。README等约定名称保持现有大小写，避免在不同操作系统之间产生路径差异。

| 材料 | 命名格式 | 内容要求 |
| --- | --- | --- |
| 阅读笔记 | `notes/chXX-topic-author.md` | 版本与定位、学习目标、概念、推导、理解、问题、参考资料 |
| PPT | `slides/YYYY-MM-DD-chXX-topic.pptx` | 学习目标、核心概念、推导、示例、个人思考、讨论问题、参考资料 |
| PPT展示版 | 与可编辑文件同主体的 `.pdf` | 与对应源文件同步更新 |
| Demo | `demos/chXX-topic/README.md` | 环境、步骤、结果判定、实测证据、限制和许可 |
| 习题解答 | `exercises/chXX-exNN-topic-author.md` | 题号、假设、原创解答、检查和错误分析 |
| 实际研讨记录 | `sessions/YYYY-MM-DD.md` | 真实日期、参与者、材料、结论和后续任务 |

`XX`是正式章号，至少两位。`NN`是题号；需要区分小题时，在主题中写明，例如 `ch03-ex02-part-a-yourname.md`。跨章材料选择主章号，并在正文列出完整范围。附录材料先在任务Issue中约定与主章的关联，避免自行制造正式章号。

PPT日期优先采用已确认的研讨日期。研讨尚未定期的草稿可以使用真实材料创建日期，并在PR中说明。会后记录的日期必须是实际发生日期，不能用创建文件的日期代替。

材料增加后，可在笔记、PPT或习题目录内按 `chXX/` 分组，但不要预建没有内容的章节树。Demo直接放在 `demos/chXX-topic/`，使成员能快速找到运行入口。图片等辅助文件使用有意义的英文名，并在材料中通过相对链接引用。

同一文件修订时沿用原路径，由Git保留历史。确需调整文件名时使用普通重命名并同步修改引用链接；不要用 `final-final`、`new-copy` 等名称代替版本管理。不同成员提交同一主题时增加作者或主题细分，不覆盖他人文件。

## 一次研讨的完整流程

以下时间是默认准备节奏，可按章节难度、成员时间和Demo规模共同调整。T表示实际研讨日，所有具体安排仍需要确认。

| 节点 | 工作 | 可检查的产出 |
| --- | --- | --- |
| T−7天 | 确认章节、目标、汇报人、审阅人和时间 | 研讨任务Issue及整体日程 |
| T−3天 | 提交阅读笔记、PPT初稿及适用Demo | 草稿PR、材料路径和验证状态 |
| T−1天 | 检查来源、推导、运行条件和讨论重点 | 审阅意见、修订内容及待讨论清单 |
| T日 | 汇报、讨论和实际演示 | 实际观察、讨论结论、分歧与遗留问题 |
| T+2天 | 修订材料、完成记录和分派后续任务 | 最终材料PR、日期记录及任务负责人 |

在Issue里写清目标和完成条件，例如“能够解释演化域的作用并指出模型假设”，比“完成第2章”更便于审阅。没有适用Demo的章节可以只提交笔记、PPT和推导，不应为满足形式要求编造实验。

延期时更新整体日程并说明原因。尚未发生的研讨留在计划与Issue中，不在 `sessions/` 创建一份看似已经完成的记录。若草稿提前合并，草稿状态和未完成内容仍须保留。

## 提交第一份笔记与PPT

本节命令适用于仓库已经发布、具有正常访问权限的环境。已有本地克隆时直接进入该目录，不要重复克隆覆盖原文件。

### 获取仓库与创建分支

首次获取仓库：

```sh
git clone https://github.com/CPS-HCPS-Research/Book-Reading-Seminar.git
cd Book-Reading-Seminar
```

开始工作前检查状态。在工作区干净时更新主分支，再创建工作分支：

```sh
git status --short --branch
git switch main
git pull --ff-only
git switch -c materials/lfcps-ch02-domain-study
```

`materials/lfcps-ch02-domain-study`只是英文分支命名示例，不代表已安排该任务。若分支已经存在，继续使用该分支或换一个有意义的新名称。发现未提交改动时先确认其归属，不使用清理或重置命令丢弃它们。

### 准备阅读笔记

以下示例复制笔记模板。将 `yourname` 换成自己的英文标识；不要覆盖已有同名笔记。

```sh
cp -n templates/notes.md books/LFCPS/notes/ch02-domain-study-yourname.md
```

填写模板要求的元信息和各节内容，删除未填占位符，确认正文中的路径相对于笔记文件所在位置。新增材料后，在 `books/LFCPS/notes/README.md` 增加索引行，注明作者与草稿或审阅状态。

### 准备PPT

用熟悉的演示软件制作汇报，按[汇报模板](../templates/presentation.md)安排内容。将可编辑文件保存到 `books/LFCPS/slides/`，建议同时导出同名PDF。

```text
books/LFCPS/slides/YYYY-MM-DD-ch02-domain-study.pptx
books/LFCPS/slides/YYYY-MM-DD-ch02-domain-study.pdf
```

以上日期为格式占位，保存前必须替换为真实日期。可编辑格式还支持 `.odp` 或 `.key` 文件；不要求将整套幻灯片转换成Markdown。提交前打开源文件和PDF检查字体、公式、图片、页面布局和参考资料，更新 `slides/README.md` 的索引。

### 本地检查与提交

在仓库根目录运行：

```sh
python3 scripts/check_repository.py
git status --short
git diff --check
```

通过后，只暂存本次确实准备好的文件。例如以下命令适用于已经填写完成的笔记和笔记索引，执行前替换作者标识：

```sh
git add -- books/LFCPS/notes/ch02-domain-study-yourname.md books/LFCPS/notes/README.md
git diff --cached --stat
git diff --cached
```

PPT、PDF和其索引也按实际完整路径单独暂存；不要直接暂存整个工作目录。二进制文件的差异不容易通过Git阅读，因此需要人工打开确认。

确认暂存内容正确后提交并推送工作分支：

```sh
git commit -m "添加LFCPS第2章学习材料"
git push -u origin materials/lfcps-ch02-domain-study
```

随后在GitHub建立目标为 `main` 的PR，按下一节的要求说明内容与审阅需求。

## 提交第一个实验与演示

实验与演示（Demo）可以是原创程序、形式化模型、证明脚本或可重复操作的工具演示。每个Demo都有独立目录和README；具体代码与工具版本由实际任务决定。

### 建立目录与运行说明

下列命令仅建立说明文件，不会实现、安装或验证任何案例。执行前确认主题和对应章节，并检查目录是否已有他人的工作：

```sh
mkdir -p books/LFCPS/demos/ch02-domain-study
cp -n templates/demo.md books/LFCPS/demos/ch02-domain-study/README.md
```

根据实际实现添加源码、模型、配置和必要的依赖说明。README中至少写明：

| 项目 | 应回答的问题 |
| --- | --- |
| 目标与章节 | 展示哪一个问题？对应哪一版教材的哪一章或节？ |
| 理论与假设 | 模型、初始条件、规格、简化假设是什么？ |
| 语言与工具 | 使用哪些语言、工具、后端和精确版本？ |
| 环境与依赖 | 操作系统、运行时、依赖、获取方式和许可要求是什么？ |
| 安装方式 | 如何从干净环境开始配置？命令在哪里执行？ |
| 执行步骤 | 输入文件、参数、命令或GUI操作是什么？ |
| 预期输出 | 执行前设定的输出和成功判定条件是什么？ |
| 实际结果 | 谁在何时执行了什么版本？观察到了什么？证据在哪里？ |
| 结果解释 | 结果支持什么结论？有哪些不支持的外推？ |
| 限制与来源 | 有哪些未验证条件？代码、模型和数据来自哪里？ |

路径和命令必须能让另一位成员找到相同输入。尽量将依赖版本写入适合该语言的依赖说明文件，但不要把第三方依赖目录或工具发行包复制进仓库。

### 如实记录验证状态

| 状态 | 使用条件 |
| --- | --- |
| 未运行 | 尚未执行，或缺少实际环境；写明阻碍 |
| 运行失败 | 已执行但未满足判定条件；记录错误和复现方式 |
| 运行通过 | 所列环境、输入和步骤下满足明确判定条件 |
| 独立复核通过 | 另一位成员实际复核，并留下人员、环境、日期和结果 |
| 不适用 | 本次材料不需要Demo或某项验证；说明理由 |

预期输出必须与实测输出分开。不得把示例文本、预期截图、历史工具宣传或其他人的运行记录写成本次结果。CI检查通过也不表示Demo已经执行。

LFCPS的KeYmaera X实验还应说明混合系统模型、dL规格、初始条件、演化域、工具和算术后端版本、证明是否闭合及残留子目标。数值轨迹没有违反约束，不等于所有允许行为的安全性已得到证明。

可把必要的小型脱敏证据放在Demo的 `evidence/` 中，使用有意义的英文 `.txt` 或 `.json` 文件名，并记录实际命令、输入和提交版本。不要批量加入日志、缓存、安装包或巨大数据。无法提供环境时，可以提交标为“未运行”的草稿说明供审阅，不填写成功结果。

完成后更新 `books/LFCPS/demos/README.md` 的索引，运行仓库检查，再将本次Demo的具体文件加入同一任务PR或独立关联PR。

## 通过合并请求协作

任务单（Issue）用于明确任务和跟踪问题；分支用于隔离修改；提交记录一批相关变化；合并请求（Pull Request，简称PR）用于审阅和合并。日常材料通过PR进入 `main`，不要让多位成员直接修改主分支。

### 选择任务与问题模板

| 模板 | 适用情形 |
| --- | --- |
| 新教材研读提议 | 讨论另一教材的研究价值、版本、先修知识、范围和组织安排 |
| 研讨任务安排 | 确认章节、人员、时间、材料与准备节点 |
| 学习问题与勘误反馈 | 提交可定位的概念、推导、仓库材料、Demo或失效链接问题 |

模板位于 [.github/ISSUE_TEMPLATE](../.github/ISSUE_TEMPLATE/)。疑似教材错误应先查官方勘误，并将“怀疑有误”和“已确认错误”分开。

### 填写合并请求说明

PR模板位于 [.github/PULL_REQUEST_TEMPLATE.md](../.github/PULL_REQUEST_TEMPLATE.md)。每次提交需说明修改内容、教材版本和章节、材料路径、Demo验证状态与证据、版权与第三方来源、未完成项、审阅人及审阅重点。

未完成材料可以先建立草稿PR。填写检查框应基于实际检查；不适用时在对应字段说明原因，而不是把所有项目机械地勾选为完成。代码或推导使用AI辅助时，写明辅助范围与人工核对情况，提交者仍对内容负责。

审阅人可以要求修改或说明。汇报人在同一工作分支追加普通提交，PR会体现更新；关键讨论应在PR或Issue中留存，避免只在聊天中口头确认。合并后更新章节任务和材料索引，必要时把尚未完成事项拆成新的任务Issue。

### 没有直接写入权限

可以先Fork仓库，克隆自己的Fork，在自己的分支提交和推送，再向 `CPS-HCPS-Research/Book-Reading-Seminar` 的 `main` 提交PR。此时 `origin` 应是自己的Fork；更新时可将组织仓库配置为 `upstream`。操作前先查看 `git remote -v`，确认不会把工作分支推到错误仓库。

### 主分支更新或出现冲突

在工作区干净、已经确认 `origin` 指向组织仓库的情况下，可在自己的工作分支中更新：

```sh
git fetch origin
git merge origin/main
```

Fork协作对应使用已配置的 `upstream/main`。出现冲突时逐段确认双方意图，解决后重新检查并提交；无法判断材料归属或正确版本时请相关作者共同处理，不通过强推覆盖他人内容。

## 研讨记录与知识追踪

实际研讨结束后，从[session模板](../templates/session.md)创建 `sessions/YYYY-MM-DD.md`。同日多场会议在同一文件中分节，并注明时间、主题和参加人员。

记录应包括教材版本与章节、实际日期与时区、汇报人和参与者、PPT/笔记/Demo链接、核心知识点、重点问题与结论、未解决问题，以及带有负责人和状态的后续任务。

从 `sessions/` 引用教材材料时，路径从仓库根目录的下一级开始计算。以下仅是链接格式示意，文件名和日期必须换为实际存在的材料：

```markdown
[汇报PPT](../books/LFCPS/slides/YYYY-MM-DD-ch02-domain-study.pptx)
[Demo说明](../books/LFCPS/demos/ch02-domain-study/README.md)
```

除了方便访问的相对链接，还应记录研讨当时使用的提交SHA或材料PR。若需要精确复原当时内容，可在GitHub文件页面切换到对应提交，再复制永久链接。后续材料修订不会改变当时使用的版本说明。

后续任务只有在完成条件满足并有材料或审阅证据时才标为“已完成”。没有结论时写“尚未解决”；存在不同判断时保留分歧及各自依据，不将所有讨论整理成虚构共识。会后同步更新 `sessions/README.md` 和整体日程中的记录链接。

## 版权与材料来源

优先保存官方链接、书目信息、原创学习材料及确认允许公开使用的资源。教材全文、盗版扫描件、许可不明的课件和受限教师解答不得擅自上传。互联网可下载、机构可访问或仅供学习使用，均不能直接作为在公开GitHub仓库再分发的依据。

| 材料类型 | 处理方式 |
| --- | --- |
| 原创笔记、PPT和习题解答 | 标明作者、引用和许可状态，确认有权公开 |
| 官方教材、课件、视频 | 默认登记官方入口，不镜像上传 |
| 引用的图片、文字、代码 | 明确出处、定位、版本及公开使用依据 |
| 第三方代码、模型或数据 | 核对其许可和再分发条件；不明确时仅给引用与获取链接 |
| 原创Demo代码 | 记录作者和许可状态；单独采用许可证时明确适用范围 |

仓库没有统一开源许可证。原创文字、代码和第三方材料的权利应分别记录，不以某段代码的许可证覆盖整本教材或整套课件。具体要求见[版权与授权规则](../CONTRIBUTING.md#版权来源与授权)。

发现凭据或敏感数据误提交时立即通知维护者并处理实际暴露的凭据。删除当前文件不能消除历史记录；涉及历史改写的处理应另行确认，不能直接破坏远程历史。

## 自动检查与人工审查

### 运行检查

检查器只使用Python标准库，需要Python 3.9或更高版本。从仓库根目录执行：

```sh
python3 --version
python3 scripts/check_repository.py
```

默认检查Git已跟踪文件和未被忽略的新文件，已跟踪但后来加入忽略规则的文件仍会检查。检查当前工作目录中的所有文件时可使用：

```sh
python3 scripts/check_repository.py --all-files
```

该模式可能报告仅存在于本机的虚拟环境、缓存和临时文件，不表示这些文件已经提交。应先用 `git status` 确认范围，不能因为提示就删除自己的必要环境。默认检查不会遍历历史提交。

修改检查器或检查规则时运行其测试：

```sh
python3 -m unittest discover -s scripts/tests -v
```

日常纯文档变更运行仓库检查和差异检查即可；不需要为每份笔记重复建立一套测试。

### 检查范围

| 项目 | 自动检查能力 | 仍需人工确认 |
| --- | --- | --- |
| 教材结构 | 必需文件和材料入口是否存在 | 档案信息是否真实完整 |
| Markdown链接 | 常规相对链接、引用式链接和常见标题锚点 | 外链可用性、复杂语法与实际内容 |
| 文件命名 | 常见材料名称、日期格式、Demo目录名称 | 章号、主题和作者是否对应实际内容 |
| Demo | 是否具有README入口 | 安装是否成功、步骤能否复现、结论是否成立 |
| PPT及PDF | 名称及PDF的同名可编辑源文件 | 排版、公式、版权与内容质量 |
| 文件大小 | 超过10 MiB警告，超过25 MiB报错 | 是否可以压缩或改为合法外部资源链接 |
| 凭据与临时文件 | 常见敏感文件名、凭据模式、缓存及生成文件 | 二进制内部内容、历史泄露、未覆盖的敏感信息 |

脚本退出码为0表示没有发现错误，仍应查看警告；非0表示需要处理报告中的错误。仓库检查通过不意味着版权已审核、推导已证明或Demo已正确运行。

### GitHub自动检查

工作流文件为 [.github/workflows/check.yml](../.github/workflows/check.yml)，在推送、提交PR和手动触发时运行，使用只读仓库权限。任务名为 `repository-check`，执行结构检查和检查器测试，不安装或执行学生Demo。

工作流必须成功发布到远程且符合组织的Actions策略才会实际运行。管理员应在检查已经出现并成功运行后，将其纳入主分支保护要求。具体设置见[维护说明](maintenance.md)。

## 增加第二本教材

先使用教材提议Issue讨论研究价值、版本、先修知识、拟读章节和负责人，确认后选择唯一稳定ID。不要把另一本书放进LFCPS目录，也不要因为新教材暂时无材料而预建大量空章节。

以下以 `NEWBOOK` 作为操作占位符，执行前必须替换为已确认的英文教材ID；它不代表已批准的第二本教材。

```sh
git switch -c books/newbook-setup
mkdir -p books/NEWBOOK/notes books/NEWBOOK/slides books/NEWBOOK/demos books/NEWBOOK/exercises
cp -n templates/book.md books/NEWBOOK/README.md
```

然后完成以下工作：

1. 填写教材README的全部档案字段，核对官方书目、版次和正式章号；未指定负责人如实标记。
2. 编写 `schedule.md`，说明拟读范围和任务进度；具体日历仍链接到根目录的 `SCHEDULE.md`。
3. 编写 `resources.md`，登记官网、出版社、DOI、合法获取方式、版权限制与核实日期。
4. 为 `notes/`、`slides/`、`demos/`、`exercises/` 各写一个README，说明材料规则与实际状态。可以参考LFCPS的分类结构，但不要保留错误书名、路径或示例成果。
5. 把教材模板中的材料路径转换成指向真实文件的Markdown链接；删除所有未填写占位符。
6. 更新根目录 `CATALOG.md` 和 `README.md` 的教材入口。有实际安排后再更新整体日程。
7. 运行仓库检查，暂存具体文件，通过PR审阅后合并。

添加一本书不需要修改检查器中的教材名单。检查器根据 `books/` 下的实际目录检查必需文件，因此同样适用于后续教材。

## 维护与常见问题

### 每轮研读结束后的维护

负责人核对本轮约定范围、材料索引、会后记录和未解决任务。维护者检查失效链接、工具版本及资料授权状态，确认后更新教材状态。已有材料通过普通提交修正，保留可编辑源文件和Git历史，不建立多个“最终版”目录。

维护者应在README、协作规范、说明文档和检查器规则之间保持一致。修改规范时，在同一PR中更新相应文档；涉及检查器行为时运行测试。实际日程、教材元数据和材料清单仍分别由其专门文件维护，不在本说明反复抄录。

### 常见问题处理

| 问题 | 处理方法 |
| --- | --- |
| 材料文件名能否用中文 | 不使用中文路径；中文标题和正文放在文件内容中 |
| 只有PDF能否提交汇报 | 补充同名可编辑源文件；不要把官方课件PDF当成学生原创汇报 |
| 研讨日期尚未确定 | 草稿使用真实创建日期并说明；整体安排写待定 |
| Demo没有运行环境 | 保持未运行，写明依赖和阻碍；不得填写成功输出 |
| 检查提示缺失链接 | 检查文件名大小写、相对路径、目标文件是否纳入本次提交 |
| 忽略规则加入后仍报敏感文件 | 文件可能已被Git跟踪；先确认暂存和历史情况，由维护者处理 |
| PPT超过大小限制 | 压缩图片和媒体；大型资源采用获准的外部存储并记录版本与获取方式 |
| 书的官方链接失效 | 提交问题Issue，查找官方替代入口，不改成来源不明的下载站 |
| 两个人修改同一索引 | 审阅合并双方新增行，确认链接和内容，没有必要覆盖整份文件 |
| 本地检查通过但CI失败 | 对照CI日志检查提交文件是否齐全、路径大小写和Python环境差异 |
| Git推送被拒绝 | 读取错误；区分网络、认证、权限、分支保护与历史分歧，不使用强推兜底 |
| 需要纠正已经合并的内容 | 通过新PR修正并关联原问题；保留历史和必要的勘误说明 |
